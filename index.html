Then I built it again by hand, with no generator

A generated config proves the tooling works. It does not prove I can defend a line of it. So I booted three switches with no configuration at all and typed every command at the CLI — addressing, network-instances, ASNs, peer groups, neighbours, export policy.

It broke three times, and none of them were BGP problems:

  • The commit was refused — address is a list, so a second set appended instead of replacing and one interface held both /31s. That assumption came straight from IOS, where ip address replaces.
  • Session stuck at active — port up, subinterface down, reason no-ip-config. SR Linux has three separate admin-states where IOS has one no shutdown.
  • Ping succeeded and the session still would not come up — connect-retry defaults to 120 seconds. The generator had been setting it to 5 all along; that line only stopped being noise once I hit the problem myself.

Each was found by reading what the device actually printed and testing one layer at a time from the bottom up. Final result: ttl=61 host to host — 64 minus the three routers the packet crossed — at 0% loss.

Incident write-ups

Two real failures, including the wrong turns. Both have the same shape.

Four nodes down, every switch port healthy

A four-node cluster vanished from the network while the managed switch reported 1G Full on every one of its ports — the signal that normally means "cabling is fine, the machine is broken."

Root cause: Linux names USB NICs from their MAC address, so relocating an adapter silently renames the interface and orphans the bridge member. The adapter still negotiates link in the PHY, which is why Layer 1 kept insisting everything was fine.

Also covers a monitoring bug worth knowing: Windows ping returns exit code 0 for Destination host unreachable, so a watcher that trusts $? reports dead hosts as alive.

Gateway cutover with no DHCP and no error

Replacing a consumer router with a VLAN-capable gateway on a live network, under a constraint that no device be re-addressed. Two failures, neither of which logged anything anywhere.

  • The switch was in a WAN-capable port configured as WAN, so the gateway treated the entire LAN as an internet connection.
  • The bridge-mode modem was still bound to the old router's MAC — diagnosed from a single traceroute hop showing 169.254.x.

The absence of an error message is not evidence that nothing is wrong. It often means the failure is a valid state nobody intended.
