The fourth assertion is the one that matters. It is what stops the documentation drifting away from the fabric.

How the configs are generated

fabric.yml is the intent. gen_configs.py renders all six switch configs from it, deriving the point-to-point addressing rather than hand-listing it. CI regenerates and fails the build if configs/ drifts from the model.

The same source-of-truth pattern a NetBox-driven pipeline uses, in miniature. The rule it enforces: fix the generator, never the rendered artifact.

Then I built it again by hand.It broke three times.

A generated config proves the tooling works. It does not prove I can defend a line of it.

So I booted three switches with no configuration at all and typed every command at the CLI — addressing, network-instances, ASNs, peer groups, neighbours, export policy. No generator, no startup-configs.

None of the three faults were BGP problems. Each was found by reading what the device actually printed and testing one layer at a time from the bottom up.

The commit was refused

address is a list, so a second set appended instead of replacing — one interface ended up holding both /31s, and the commit rejected the whole transaction.

That assumption came straight from IOS, where ip address replaces. The fix was a delete, not another set. Nothing reached the forwarding plane, which is exactly what a candidate config is for.

Session stuck at active

Port up, subinterface down, reason no-ip-config — printed right there in show interface.

SR Linux has three independent admin-states: the port, the subinterface, and ipv4 itself, where IOS has one no shutdown. All three need enabling, on both ends of the link.

Ping worked. Session still would not come up.

Layer 3 was fine at 0% loss, which ruled out addressing entirely and left the protocol timer. connect-retry defaults to 120 seconds.

The generator had been emitting timers connect-retry 5 from the start. That line only stopped being noise once I hit the problem by hand — which is the whole argument for doing it this way.

ttl=61 · 0% packet loss, host to host

ttl=61 is the proof. Alpine sends at 64; three routers decremented it. Nothing was bridged.

In both, the most authoritative signal was measuring the wrong question.

Layer 3 — the question being asked

A four-node cluster vanished from the network while the managed switch reported 1G Full on every one of its ports — the signal that normally means "cabling is fine, the machine is broken."

Root cause: Linux names USB NICs from their MAC address, so relocating an adapter silently renames the interface and orphans the bridge member. The adapter still negotiates link in the PHY, which is why Layer 1 kept insisting everything was fine.

A monitoring bug worth knowing

Windows ping returns exit code 0 for Destination host unreachable — that reply comes from a neighbour rejecting the packet, not from the target answering.

A watcher that trusts $? therefore reports dead hosts as alive. Mine did, which is why the first round of diagnosis went nowhere. The correct test matches the reply text, not the exit code.

Gateway cutover with no DHCP and no error

Replacing a consumer router with a VLAN-capable gateway on a live network, under a constraint that no device be re-addressed. Two failures, neither of which logged anything anywhere.

  • The switch was in a WAN-capable port configured as WAN, so the gateway treated the entire LAN as an internet connection.
  • The bridge-mode modem was still bound to the old router's MAC — diagnosed from a single traceroute hop showing 169.254.x.

What made the migration move nothing: the old router had been handing out the entire subnet as its DHCP pool, overlapping every static address on the network. Narrowing the new pool to .50–.99 is why every device came back on the address it already had.

The absence of an error message is not evidence that nothing is wrong. It often means the failure is a valid state nobody intended.
